운영 중인 결제 모듈의 코드를 읽다가 도저히 이해할 수 없는 한 줄과 마주쳤다. 멀쩡히 잘 계산된 환불 수수료에 왜 하필 `Math.max(0, fee - 10)`이라는 정체불명의 보정식을 거쳐서 반올림을 하는지 아무런 주석도 없었기 때문이다. 혹시 불필요한 레거시 코드인가 싶어 지우려던 찰나, 등골이 서늘해져 에디터의 `Git Blame` 단축키를 눌렀다.

화면에 떠오른 작성자의 이름은 다름 아닌 **6개월 전의 나 자신**이었고, 그 옆에 적힌 커밋 메시지는 단 세 글자였다.

> `fix: 오류 수정`

그 순간 과거의 내 멱살을 잡으러 타임머신을 타고 싶은 심정이었다. ~~대체 무슨 오류를 왜 저렇게 수정했단 말인가!~~ 슬랙 검색창을 30분 동안 뒤진 끝에야, 당시 외부 PG사의 부가세 원 단위 절사 기준이 우리 내부 정산 로직과 1원 차이로 어긋나는 엣지 케이스가 있어서 임시 방편으로 넣었던 방어 코드였음을 가까스로 알아낼 수 있었다. 그날 이후 나는 커밋 메시지를 단순한 저장 로그가 아니라 **미래의 나와 동료에게 남기는 아키텍처 결정 기록(ADR)**으로 대하기 시작했다.[^1]

---

## 1. '무엇(What)'은 `git diff`가 이미 알고 있다

초보 시절 내가 썼던 커밋 메시지들을 돌아보면 한결같이 **코드 변경 사항을 한국어로 그대로 번역해 놓은 수준**이었다.

- `feat: OrderService.ts에 timeout 파라미터 추가`
- `fix: null 체크 조건문 추가`
- `refactor: 변수명 변경 및 함수 분리`

하지만 생각해보면 어떤 파일의 몇 번째 줄에 `null` 체크가 추가되었는지는 `git show`나 `git diff` 명령어만 쳐도 1초 만에 알 수 있다. 정작 6개월 뒤 그 코드를 유지보수하는 개발자가 피 토하며 알고 싶어 하는 정보는 코드 자체에는 적혀 있지 않은 **맥락(Context)과 이유(Why)**다.

### 1.1 나쁜 커밋 메시지와 좋은 커밋 메시지의 결정적 차이

방금 언급했던 `timeout` 파라미터 변경 사례를 두고, 정보량이 없는 커밋과 맥락이 살아있는 커밋을 비교해 보자.

```text title="나쁜 커밋 메시지 예시 (What만 나열함)"
fix: 외부 배송 조회 API 타임아웃을 3000ms에서 8000ms로 변경

- deliveryClient.ts의 axios timeout 설정값 수정
- 재시도 횟수를 3회에서 1회로 축소
```

위 메시지에는 **"왜 타임아웃을 늘리면서 오히려 재시도 횟수는 줄였는지"**에 대한 설명이 전혀 없다. 누군가는 나중에 *"재시도는 많을수록 안전한 것 아닌가?"*라며 다시 3회로 되돌렸다가 장애를 재발시킬 것이다. 반면 아래와 같이 작성된 커밋 메시지는 그 자체로 완벽한 방패가 된다.

```text title="좋은 커밋 메시지 예시 (Why와 배경, 트레이드오프를 기록함)"
fix(delivery): 월요일 오전 택배사 API 지연으로 인한 재시도 폭풍(Retry Storm) 방지

[문제 배경]
매주 월요일 09:00~10:00 사이 주말 물량 집계로 인해 대한통운 송장 조회 API의
P99 응답 시간이 평소 400ms에서 최대 6.5초까지 급증하는 현상이 확인됨.

[원인 및 해결]
기존 3초 타임아웃 + 3회 즉시 재시도 설정에서는 3초 만에 타임아웃이 발생한 뒤
동일한 무거운 쿼리를 3번 연속 재호출하여 상대 서버의 Rate Limit(429) 차단을 유발함.
이에 따라 단일 요청 타임아웃을 8초로 넉넉히 늘려 첫 요청의 성공률을 확보하는 대신,
자동 재시도는 1회로 제한하여 연쇄 장애를 차단함.

Refs: #412, Jira-OPS-891
```

> [!IMPORTANT]
> **커밋 본문(Body)을 채우는 3단 공식**
> 1. **현상과 문제(Problem)**: 변경 전 시스템이나 사용자가 겪던 구체적인 불편함이나 버그 증상
> 2. **원인과 판단(Why)**: 여러 대안 중 왜 하필 지금의 코드 수정 방식을 선택했는지(기각된 대안 포함)
> 3. **부수효과 및 한계(Caveats)**: 이 변경으로 인해 달라지는 동작이나 향후 추가로 개선해야 할 지점

## 2. 원자적 커밋(Atomic Commit): 되돌릴 수 없는 뭉뚱그리기 피하기

아무리 커밋 메시지를 정성껏 쓰더라도, 하나의 커밋 안에 **서로 다른 성격의 변경 사항이 뒤섞여 있다면** 그 가치는 반감된다. 예를 들어 버그 하나를 고치러 들어갔다가 눈에 거슬리는 주변 코드의 들여쓰기를 고치고, 변수명을 바꾸고, 새로운 유틸 함수를 추가한 뒤 한 번에 `git add .`를 치는 습관이다.

### 2.1 거대한 단일 커밋 vs 원자적 분리 커밋 워크플로우

만약 운영 서버 배포 직후 치명적인 사이드 이펙트가 발견되어 `git revert`를 해야 하는 상황을 상상해 보자. 리팩토링과 기능 수정이 한 커밋에 뭉쳐 있으면 버그 수정만 쏙 빼내어 롤백하는 것이 불가능하다.

```mermaid
flowchart TD
    subgraph Bad["나쁜 습관: 작업 끝난 뒤 git add . 한 번에 커밋"]
        B1["파일 18개 수정 (포맷팅 + 변수명 변경 + 결제 버그 수정)"] --> B2["단일 커밋 생성: 'fix: 결제 오류 수정 및 코드 정리'"]
        B2 --> B3["장애 발생 시 git revert 시도 -> 리팩토링까지 전부 충돌하며 롤백 실패!"]
    end

    subgraph Good["좋은 습관: git add -p 로 논리적 단위별 원자적 커밋"]
        G1["1단계 커밋: style: 결제 모듈 Prettier 포맷팅 일괄 적용"] --> G2["2단계 커밋: refactor: 할인율 계산 로직을 순수 함수로 추출"]
        G2 --> G3["3단계 커밋: fix(payment): 소수점 이하 부가세 원 단위 절사 오차 수정"]
        G3 --> G4["장애 발생 시 3단계 커밋만 안전하고 즉각적으로 Revert 가능!"]
    end
```

### 2.2 `git add -p`를 활용한 코드 조각 단위 스테이징

이미 한 파일 안에서 리팩토링과 버그 수정을 동시에 해버렸다면 어떻게 해야 할까? 이때 나를 구원해 주는 최고의 도구가 바로 **인터랙티브 패치 스테이징(`git add -p` 또는 `git add --patch`)**이다.[^2]

```bash title="터미널에서 파일 내 특정 코드 블록(Hunk)만 골라서 커밋하기"
# 파일 전체가 아니라 변경된 코드 덩어리(Hunk) 단위로 대화형 선택 시작
$ git add -p src/services/paymentService.ts

# 출력되는 프롬프트에서 단축키로 제어:
# y : 이 코드 덩어리를 이번 커밋에 포함 (Stage this hunk)
# n : 이 코드 덩어리는 다음 커밋으로 미룸 (Do not stage)
# s : 덩어리가 너무 크면 더 작은 단위로 쪼개기 (Split into smaller hunks)
# e : 줄 단위로 직접 편집해서 스테이징 (Manually edit current hunk)
```

VS Code나 Cursor 같은 에디터를 쓴다면 좌측 소스 제어 탭에서 원하는 코드 라인만 마우스로 드래그한 뒤 우클릭하여 **Stage Selected Ranges**(<kbd>Ctrl</kbd> + <kbd>K</kbd>, <kbd>Ctrl</kbd> + <kbd>Alt</kbd> + <kbd>S</kbd>)를 누르면 1초 만에 깔끔하게 분리할 수 있다.

> [!TIP]
> **동작 변경 없는 리팩토링과 실제 로직 변경은 무조건 커밋을 나누세요**
> 파일 이동(`git mv`)이나 변수명 일괄 변경(`refactor`) 커밋에는 **단 한 줄의 비즈니스 로직 변경도 포함되지 않게** 유지하세요. 그러면 코드 리뷰어도 30개 파일이 바뀐 리팩토링 커밋은 10초 만에 훑어 넘기고, 진짜 로직이 바뀐 5줄짜리 `fix` 커밋에만 온전히 집중할 수 있습니다.

## 3. Conventional Commits 접두사 실전 판단 기준표

팀마다 `feat`, `fix`, `refactor`, `chore`를 붙이는 기준이 모호해 자주 논쟁이 벌어지곤 한다. 우리 팀이 정립하여 사용 중인 명확한 판별 기준은 아래와 같다.

| 커밋 타입 | 프로덕션 코드 변경 여부 | 외부에서 관찰 가능한 동작 변화 | 실무 적용 판단 기준 및 예시 |
| :--- | :---: | :---: | :--- |
| **`feat`** | O | **O (신규 기능 추가)** | 사용자나 클라이언트에게 새로운 기능, API 엔드포인트, UI 옵션이 추가됨 |
| **`fix`** | O | **O (비정상 -> 정상 교정)** | 기획 의도와 다르게 동작하던 버그, 예외 누락, 레이아웃 깨짐을 수정함 |
| **`refactor`** | O | **X (동작 100% 동일)** | 내부 구조 개선, 함수 추출, 타입 정교화 등 외부 동작 변화 없는 코드 재구성 |
| **`perf`** | O | **△ (속도/메모리 개선)** | 기능은 같으나 쿼리 인덱싱, 메모이제이션 등으로 응답 속도나 리소스를 최적화함 |
| **`test`** | X (테스트 파일만) | X | 단위/통합 테스트 추가 및 수정 (프로덕션 코드는 한 줄도 바뀌지 않음) |
| **`chore`** | X (설정/빌드만) | X | 패키지 버전 업데이트, `.gitignore`, CI 워크플로우, 빌드 스크립트 변경 |

<details>
<summary>로컬 개발 중에는 마음껏 지저분하게 커밋하고 PR 올리기 전 정리하는 팁 (`git rebase -i`)</summary>

코드를 짜는 도중부터 완벽한 커밋 메시지를 작성하려고 하면 개발 흐름(Flow)이 끊길 수 있습니다. 그래서 저는 기능 구현 중에는 `wip: 일단 저장`, `wip: 테스트 통과`처럼 편하게 자주 커밋합니다.
대신 PR(Pull Request)을 올리기 직전에 `git rebase -i origin/main`을 실행하여 `squash`(합치기)와 `reword`(메시지 다시 쓰기)를 통해 3~4개의 깔끔한 스토리라인을 가진 원자적 커밋으로 재조립합니다.

</details>

## 4. `git bisect`가 빛을 발하는 순간

원자적 커밋과 명확한 커밋 메시지의 진가는 **언제부터 망가졌는지 모르는 은밀한 회귀 버그(Regression Bug)**를 추적할 때 폭발한다. 지난달 모바일 사파리에서만 특정 모달의 스크롤이 잠기는 버그가 발견되었는데, 최근 2주간 쌓인 커밋이 무려 120개에 달했다.

하지만 모든 커밋이 **빌드와 테스트가 통과하는 독립된 원자적 단위**로 관리되고 있었던 덕분에, `git bisect`(이진 탐색 디버깅)를 실행하여 단 7번($\log_2 120 \approx 7$)의 체크아웃 만에 범인이 된 CSS 수정 커밋을 정확히 찾아낼 수 있었다.

> [!WARNING]
> **깨진 중간 커밋(Broken Commit)을 남기지 마세요**
> 히스토리 중간에 타입 에러나 빌드 에러가 나는 미완성 커밋이 끼어 있으면 `git bisect`를 돌릴 때 해당 지점에서 빌드가 깨져 자동화된 원인 추적이 불가능해집니다.

## 5. `git commit` 엔터를 누르기 전 10초 점검 리스트

오늘도 나는 터미널에서 커밋 에디터를 띄울 때마다 아래 5가지 질문에 모두 체크 표시를 할 수 있는지 점검한다.

- [x] `git diff --staged`를 눈으로 한 번 훑어보며 `console.log`나 주석 처리된 임시 코드가 섞여 들어가지 않았는지 확인했는가?
- [x] 커밋 제목(첫 줄)을 50자 이내의 명확한 개조식 문장으로 작성하여 `git log --oneline`만 봐도 의도가 드러나는가?
- [x] 리팩토링(구조 변경)과 버그 수정/기능 추가(동작 변경)가 하나의 커밋에 뒤섞여 있지 않은가?
- [x] 코드만 봐서는 알 수 없는 **비즈니스 제약 조건, 엣지 케이스, 대안 기각 사유**가 있다면 본문(Body)에 남겼는가?
- [ ] 6개월 뒤 새벽 2시에 장애 대응 중인 내가 이 커밋 메시지를 읽었을 때 과거의 나에게 고마워할 만큼 친절한가?

## 6. 마치며: 코드는 스냅샷이고, 커밋 히스토리는 영화다

소스 코드 파일은 시스템의 **'현재 순간을 찍은 사진(Snapshot)'**일 뿐이다. 그 사진 속 인물들이 왜 그런 표정을 짓고 그 자리에 서 있게 되었는지 인과관계를 설명해 주는 것은 오직 **커밋 히스토리라는 '영화(Timeline)'**뿐이다.

오늘 커밋 메시지를 적을 때 귀찮다고 `fix: 수정`이라고 적으려던 손을 잠시 멈추고, 미래의 나에게 짧은 편지 한 통을 남기는 마음으로 두세 문장의 이유를 덧붙여 보자. 그 1분의 투자가 언젠가 당신의 주말과 퇴근 시간을 지켜줄 가장 든든한 보험이 될 것이다.

[^1]: 아키텍처 결정 기록(ADR: Architecture Decision Record)은 거창한 위키 문서에만 존재하는 것이 아닙니다. 코드 라인과 가장 밀접하게 결합된 불변의 저장소인 Git 커밋 로그야말로 절대 유실되지 않는 최고의 마이크로 ADR입니다.
[^2]: Git 공식 문서의 *Interactive Staging* 섹션에서 다루는 기능으로, 하나의 파일 내에서도 서로 다른 문맥의 변경 사항을 별도의 커밋으로 쪼갤 수 있게 해주는 핵심 도구입니다.
